# Skill 效果验证

用于修改本 skill 后的行为检查，或用户明确要求比较设计效果时。普通 UI 交付无需运行整套比较。

## 行为与视觉证据分开

1. 静态检查：检查元数据、调用名称、相对引用，以及随 skill 打包的执行资源。通过不能代表设计有效。
2. 流程检查：给出真实请求，观察是否选择合适流程、尊重范围、复用已有规范并诚实报告验证情况。基于文本的演练标注为自查，不能记作真实生成或独立评审。
3. 实现检查：运行实际产物，捕获对应状态的截图并操作主流程。视觉、功能和执行成本分别记录。

## 代表性案例

按本次修改挑选最相关案例，无需每次全跑：

| 案例 | 观察重点 |
| --- | --- |
| 新产品页面，方向开放 | 候选方案有结构性差异；选定方向与用户、主任务一致 |
| 已有业务后台增加一个列表页 | 沿用主题和导航；支持比较与筛选；处理相关加载、空结果和失败 |
| 只修正一个对话框的窄屏遮挡 | 修改限于相关部分；不重做品牌或要求选择三套方案；焦点和关闭行为可用 |
| 用户指定视觉参考并只要静态原型 | 遵循参考和输出范围；模拟状态有说明；不声称真实业务已经接通 |
| 无截图或独立评审能力 | 据实报告缺失证据；不编造截图、独立评审或审美通过 |
| 只总结一个含前端代码的仓库，或阅读、安装、维护 skill | 围绕分析或维护交付，不新增界面、设计 brief、截图或审美要求 |
| 仅修复后端、脚本、部署配置或解释代码 | 不因软件开发、项目包含界面或历史提到 UI 而启动设计流程 |
| 同时实现一个界面与对应 API | 仅对界面部分使用设计流程，API 等部分按功能要求验证；不把 UI 产物要求带入其他工作 |

## 同条件比较

- 比较使用相同模型与配置、需求、起始项目、素材、工具、时间或额度预算。在新上下文中执行，避免前一次方案泄漏给后一次。
- 根据问题比较无 skill、原版和优化版。若全局规则强制调用本 skill，真正的无 skill 对照应在隔离环境准备；不能悄悄更改用户全局偏好。隔离不可用时只比较两个版本并标注限制。
- 生成有随机性。资源允许时对同一案例重复运行，保留所有结果与失败，不只挑最好的一次；未重复时说明只是单次观察。
- 以一致的窗口、数据、主题、缩放和状态捕获实际截图；删除版本标签再评审。评审者只接收用户任务、目标和截图，不接收 skill 版本、目标评分或实施解释。
- 分别记录：主要任务是否清楚、布局和文字、视觉一致性、适当个性；相关功能与恢复行为；耗时、轮次和改动规模。不要把三类结果压成无法解释的总分。
- 独立评审只在工具可用且当前任务允许时使用。自查不能写成独立评审；用户任务完成率需要实际用户或明确的任务测试，不能从审美评分推断。

## 最小结果记录

保留需求、初始版本、skill 内容哈希、模型/工具与预算、产物及截图位置、实际检查和失败项。结果可以用一张表记录：

| 版本 / 运行 | 视觉发现及截图 | 功能结果及证据 | 执行成本 | 限制 |
| --- | --- | --- | --- | --- |
| 实际运行标识 | 已观察到的问题或改善 | 实际执行的检查结果 | 可获得的耗时与轮次 | 缺失证据、模拟部分 |

只报告证据支持的变化，例如“窄屏主操作不再被遮挡，主路径点击通过”。少量案例不能支持普遍提升比例，主观评分也不能支持商业转化提升。失败应反馈成具体规则调整，避免把单次偏好固化成所有产品的统一风格。
