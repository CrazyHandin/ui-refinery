# 动效与交互质感

用于新增、调整或诊断实际动效，以及本次涉及的按钮、弹层和提示反馈。静态布局修改不必启动动效审查；原生应用采用平台实现，以下 CSS 与浏览器建议只用于 Web。

## 先判断用途与频率

- 说明动效解决什么：确认输入、表达状态、保持空间关系，或解释产品。高频操作应减少等待与装饰；低频引导可以有更多表现空间。
- 保留用户明确的动效方向，并让主要操作立即响应。键盘触发通常需要更克制的反馈，但触发设备本身不是禁止所有动效的理由。
- 复用已有动效变量和组件。简单状态变化优先使用现有平台能力；复杂手势、弹簧或退出编排再考虑项目已采用的工具。不要为一次淡入新增依赖。

## 按交互选择参数

以下是探索起点，服从既有主题与实际观感，不作为统一验收阈值：

| 场景 | 优先判断 |
| --- | --- |
| 按压与即时反馈 | 短促、清楚；先尝试约 100–160ms；禁用控件保持其真实状态 |
| 小弹层出现或消失 | 通常使用起步快的缓出，约 120–240ms 起试；展开起点与触发位置有关 |
| 对话框、抽屉 | 依据距离与面积选择时长，可从约 180–350ms 起试；居中对话框不强制从按钮位置缩放 |
| 屏内位置或形状变化 | 按运动关系选择缓入缓出或合适弹簧，检查中途反向与连续操作 |
| 表达性演示 | 允许更长节奏，但主要行动始终可用；重复访问时避免阻挡任务 |

先协调位置、时序和层级，再调整曲线。模糊、弹跳和逐项错峰只在确有用途时加入，不能作为掩盖布局问题的固定配方。

## 检查打断与状态一致性

- 连续打开、关闭、切换时应从当前可见状态平滑转向新目标。CSS transition、受控动画或弹簧按现有架构选择；关键帧也可使用，但需实际检查重启、取消和退出。
- 退出后移除不可见控件的交互与焦点资格；不要只把透明度设为零就留下遮挡或可聚焦元素。沿用现有弹层生命周期。
- 动画被取消、用户请求减少动态效果或时长为零时，业务状态仍应完成；不要仅依赖动画结束事件提交结果或解除锁定。
- 按压视觉反馈与真正执行操作分开。保留按钮的语义激活和键盘路径，不把提交、删除等操作提前到 pointer-down。
- 减少动态效果时削减大位移、缩放与装饰循环；按用户设置可以直接切换状态。保留可理解的静态反馈，并验证变化仍能完成。

## 性能排查先找原因

- 记录复现时的浏览器、设备、数据量与交互，再观察布局、绘制、长任务或组件频繁更新。代码检查只能形成假设；有性能记录才能确认瓶颈和改善。
- 优先尝试 `transform` 与 `opacity`，并列明需要过渡的属性。实际需要挤开周围内容的展开不能简单用缩放代替，应保留布局语义并测量代价。
- CSS 或 WAAPI 的部分动画可以交给合成线程，但属性、浏览器和运行条件都会影响结果；不能写成“CSS 动画始终不卡顿”。滤镜、裁剪和大面积阴影也需实测。
- 核对项目的 Motion 版本、API 和实际加速路径，不把 `x`、`y` 或 `scale` 的属性名当作是否加速的充分证据。当前官方文档包含可加速独立变换及环境例外的说明。
- 排查逐帧状态更新、过大的重绘区域及不必要的样式传播；有证据后再调整实现。`will-change` 只用于已定位的需要，避免全局长期添加。

## 最小复查

查看正常速度下的反馈、快速重复与反向操作、退出后的焦点，以及减少动态效果路径。必要时慢放查时序，但最终体验以正常速度为准。分别记录视觉发现、实际操作与性能证据，不从截图推断流畅度。
